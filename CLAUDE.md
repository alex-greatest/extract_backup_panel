# Инструкции для агента

Используй эти правила при работе с консольным приложением FlexRt. 

## Что это за проект

FlexRt читает скомпилированную конфигурацию панели из TIA Portal —
`pdata.fwc` из папки `Generates` проекта — и проект ПЛК (`System\PEData.plf`,
исходный или выгруженный из ПЛК) и извлекает из них данные. Цель — развивать
извлечение дальше: разбирать новые таблицы и поля. Проверено на TIA Portal
V17 и V21, панель TP700 Comfort, ПЛК S7-1500 и S7-1200.

Форматы закрытые и недокументированные. Всё, что известно о них, записано
в коде этого проекта, в этом файле, в `docs/формат-fwx/` и `docs/формат-plf/`. Часть полей
разобрана «по наблюдениям» и помечена комментариями вида «всегда 3».

Каркас формата (заголовок, TOC, каталог смещений, `STRINGSTORE`) исторически
взят из R-проекта `rois286/Flex-RT-Configuration-Editor` для WinCC flexible.
R-код не эталон и не источник требований, сверять с ним поведение не нужно.
Правильным считается то, что подтверждено байтами реального файла TIA и
решением пользователя.

Сейчас приложение за один запуск:

- печатает сводку таблиц TOC, числа строк языков, числа тегов и строку
  `Файл ПЛК:` (число ПЛК и тегов ПЛК или «не найден»);
- пишет `panel_data.xlsx` — лист «Теги» с колонками как в HMI tags в TIA,
  данные ПЛК сопоставлены по проекту ПЛК; лист «Ошибки» при проблемах проекта ПЛК;
- пишет `PDATA.xlsx` — строки всех языков, лист на каждый LCID;
- раскладывает каждую таблицу TOC в папку с hex-файлами;
- пишет лог запуска в `data/out/logs/flexrt-<дата>.log`.

Все выходы пишутся в `data/out`, а если задана непустая переменная
окружения `FLEXRT_OUT` — в эту папку с теми же именами.

Редактирования и обратной сборки FWX нет. Аргументов командной строки нет:
пути заданы константами вверху `Program.cs` — это принятое решение, а не
недоделка. Входной файл по умолчанию — `pdata.fwc` прямо в папке `Generates`
проекта TIA, проект ПЛК — `System\PEData.plf`. Переменные окружения
`FLEXRT_INPUT` и `FLEXRT_PLC`, если заданы и не пусты, подменяют эти файлы,
`FLEXRT_OUT` — каталог результата; ими пользуются проверки и тесты.

## Стек проекта

- C#, .NET 10, консольное приложение.
- ClosedXML для записи XLSX, Serilog и Serilog.Sinks.File для лога. Других
  пакетов в программе нет.
- Решение `FlexRt.sln`: программа `src/FlexRt/FlexRt.csproj` и тестовый
  проект `tests/FlexRt.Tests/FlexRt.Tests.csproj` (xUnit,
  Microsoft.NET.Test.Sdk, xunit.runner.visualstudio; ссылается на
  программу, ей открыты `internal` через `InternalsVisibleTo`).

## Структура

Исходники в `src/FlexRt/` разложены по папкам-ролям и подпапкам по смыслу,
namespace совпадает с путём папки (`Parsing/Plc/Tags/` —
`FlexRt.Parsing.Plc.Tags`):

```
Binary/                       чтение байтов, FwxFormatException
Model/    Panel/              данные панели (pdata.fwc)
          Plc/                данные проекта ПЛК (PEData.plf)
          Matching/           результат сопоставления
Parsing/  Panel/              разбор pdata.fwc
          Plc/                каркас PEData.plf (кадры, объекты, текст, связи)
              Tags/ Devices/ DataBlocks/   теги ПЛК, ПЛК и IP, DB
          Codes/              коды областей, типов, адреса (общие для панели и ПЛК)
          Matching/           TagMatcher, DbPathResolver
Export/   Tags/ Strings/ Hex/ листы «Теги»/«Ошибки», строки языков, hex; ExcelCell
Program.cs
```

`Parsing/Panel` и `Parsing/Plc` друг от друга не зависят; общее у них —
`Parsing/Codes`.

- `Program.cs` — в корне проекта, top-level statements: пять статичных
  путей (входные можно подменить `FLEXRT_INPUT` и `FLEXRT_PLC`, каталог
  выходов `data\out` — `FLEXRT_OUT`), чтение
  проекта ПЛК, сопоставление тегов, сводка в консоль, запуск трёх экспортов.
  Экспорты независимы: сбой одного не отменяет остальные.
- `Binary/` — чтение байтов файла: `FwxBinary.cs` — примитивы little endian
  (`D1`, `D2`, `D4`, `GetName`, `GetNameLen`, `GetUtf8`, `Span`, `ToHex`) с
  проверкой границ, для `.fwc` и `.plf`; `FwxFormatException.cs` — ошибка
  формата с секцией и смещением.
- `Model/` — данные разбора, по одному типу на файл: панель (`FwxDocument`,
  `HmiTag`, `PlcLink`, `HmiConnection`, …), проект ПЛК (`PlcProject`,
  `PlcDevice`, `PlcTag`, `PlcDb`, `PlcDbMember`, `PlfObject`, …), результат
  сопоставления (`PlcMatch`, `PlcLookup`).
- `Parsing/Panel/` — `FwxReader` (заголовок, TOC, `Items`/`CheckedItems` для
  таблиц «заголовок 0x34 → каталог смещений → блок данных», `TryParse`),
  `StringStoreParser`, `VarParser`, `DatalinkReadWrParser` (`DATALINK_READWR`
  и `DATALINK` — исключение из «одна таблица — один парсер»: раскладка
  элементов одна), `ConnectionParser` (`CONNECTION_OMSP`).
- `Parsing/Plc/` — `PlfReader` (единственная точка входа: кадры с SHA-256,
  актуальные версии объектов), `PlfFile` (байты + живые объекты), `PlfFormat`
  (общие константы), `PlfText` (varint, строки, мультиязычные тексты),
  `PlfRelations`; `Tags/` — `PlfTagParser`, `PlfTagNames`; `Devices/` —
  `PlfDeviceParser`; `DataBlocks/` — `PlfDbReader`, `PlfInterfaceReader`,
  `PlfInterfaceXml`, `PlfXmlBytes`, `PlfMemberComments`. Всё, кроме
  `PlfReader`, — `internal`.
- `Parsing/Codes/` — `PlcAreaCodes`, `PlcTypeCodes`, `PlcAddress`,
  `PlcMemberTypes`. `Parsing/Matching/` — `TagMatcher`, `DbPathResolver`.
- `Export/` — `Tags/PanelDataExporter` (листы «Теги» и «Ошибки»),
  `Tags/TagRowFormatter` (значения колонок), `Tags/TagTypeNames`,
  `Strings/XlsxExporter` (строки языков), `Hex/HexExporter` (все таблицы TOC),
  `ExcelCell` (обрезка текста ячейки, общая для двух Excel).
- `samples/` — реальный `pdata.fwc` (TIA V17 / TP700 Comfort, 16 записей `VAR`:
  15 тегов из HMI tags и скрытый `@DiagnosticsIndicatorTag`; копия шага 14),
  его обрезанная копия `bad.fwc` и эталонный вывод `expected/` для
  проверки перед завершением. `plc/` — `pdata.fwc` (TIA V21, 69 записей
  `VAR`, PLC-теги, два соединения) и его проект ПЛК `PEData.plf` (2 ПЛК,
  51 тег ПЛК). Эталоны: `expected/теги.txt` и `expected/plc/теги.txt` —
  слепки листа «Теги»; `expected/pdata.sha256` (264 файла) и
  `expected/plc/pdata.sha256` (386) — манифесты hex-вывода в формате
  `sha256sum` (`<хэш>  <путь через />`). Папка `expected/pdata/` с самими
  hex-файлами исключена из git и необязательна.
- `tests/FlexRt.Tests/` — `Unit/` (чистые функции: `FwxBinary`, коды и
  адреса ПЛК, `PlfText`, `ExcelCell`, `TagTypeNames`, `TagRowFormatter`) и
  `Integration/` (программа отдельным процессом на файлах `samples/`;
  испорченные входы — копии `samples/`, изменённые в рантайме). Каждый
  интеграционный тест пишет в свой временный каталог через `FLEXRT_OUT` и
  удаляет его; `data/out` тесты не трогают. Хост — `DOTNET_HOST_PATH`, иначе
  `dotnet` из PATH.
- `data/` — `out/` (результат) и `real/` — реальные копии
  `pdata.fwc`, в том числе пошаговые `real/steps/` (V17, внутренние теги) и
  `real/steps-v21/` (V21, PLC-теги). Каталог исключён из git.
- Вне репозитория, на Рабочем столе: проекты TIA `extract_backup_data\Project1`,
  `Project1_upload` (выгружен из PLCSIM), `Project1_plc_only`,
  `A603A0097_V21` / `A603A0097` (реальный, DB, 3 языка, Openness-эталон в
  `A603A0097\openness_export\`), `半自动驱动轴装配线03_06_2026[_V21]` (S7-1200).
- `.editorconfig` в корне репозитория — стиль, который проверяет сборка:
  обязательные блоки у операторов, file-scoped namespace, совпадение
  namespace с папкой.

## Модульность

- Зависимости идут в одну сторону: `Binary` ← `Model` ← `Parsing` ←
  `Export` ← `Program.cs`. Папка пользуется только теми, что левее неё:
  парсер не знает про экспортёры, экспортёр не вызывает `Parse` парсеров,
  модели зависят только от `Binary`. Namespace совпадает с папкой, поэтому
  зависимость не в ту сторону видна как неожиданный `using`.
- Одна таблица — один парсер, один выходной формат — один экспортёр. Новая
  таблица — это новые файлы (парсер и модель записи) плюс точечные строки
  подключения: список в `FwxDocument`, строка `TryParse` в `FwxReader.Read`
  и, если нужно, строка сводки в `Program.cs`. Логику существующих парсеров
  и экспортёров при этом править не приходится.
- Модели — только данные: логики разбора и форматирования в них нет.

## Источники фактов о формате

1. Код этого проекта и комментарии в нём.
2. Этот файл, `docs/формат-fwx/` и `docs/формат-plf/`.
3. Байты реального `pdata.fwc`, сопоставленные с известным проектом TIA, —
   единственный способ установить назначение нового поля. Лучший способ —
   пошаговые копии: пользователь меняет одно свойство, компилирует и
   сохраняет `pdata.fwc` под новым именем; сравниваются соседние копии.

Синтетических файлов нет и не создаётся. Копии `pdata.pwx` бесполезны: это
168-байтный зашифрованный файл администрирования пользователей, а не
конфигурация. Проверено на копиях одного тестового проекта (V17 и V21) и на
реальном проекте A603A0097 (V21, S7-1500, 3 языка); проект ПЛК — ещё на
S7-1200 без панели. Называй вывод проверенным именно на этом.

## Установленное поведение

Не меняй без решения пользователя:

- Таблица: заголовок `0x34` байта, каталог смещений по 4 байта на элемент,
  затем блок данных; смещения считаются от начала блока данных.
- Длина элемента — до следующего элемента, у последнего — до конца таблицы.
- Размер таблицы считается по физическому порядку смещений, а не по порядку
  в TOC; у последней — до `TablesEnd` из заголовка.
- Длина строки языка — до следующего смещения; если она не положительна,
  ищется нулевой символ. Хвост обрезается по первому нулю. Одинаковое
  смещение (маска `0x7fffffff`) — одна и та же строка. Строка целиком лежит
  внутри таблицы `STRINGSTORE`: выход за её конец или отсутствие нулевого
  символа до конца таблицы — ошибка формата, байты соседних таблиц в строку
  не попадают.
- Выход за границы файла даёт `FwxFormatException` с секцией и смещением.
- Сбой разбора таблицы — предупреждение, а не остановка: остальные экспорты
  всё равно отрабатывают. Строки и теги, прочитанные до сбоя, остаются в
  документе и попадают в XLSX.
- Запись `VAR`: слово 3, длина имени в символах, имя UTF-16LE, нули до
  кратности 4, u32 N — число ссылок, N ссылок по 8 байт (Id таблицы, номер
  элемента, два слова), хвост 12 байт — код типа, число элементов, `Data4`,
  нулевое слово. Хвост кончается ровно на конце элемента. N = 0 — внутренний
  тег; ссылка на `DATALINK_READWR` или `DATALINK` — связь с ПЛК (Id таблиц —
  из TOC). Запись, которая не сходится (выход за таблицу, первое слово не 3,
  несовпадение длины, ненулевые байты после имени, ненулевое последнее слово,
  массив с 0 элементов), пропускается; разбор продолжается, после таблицы одно
  сводное предупреждение (число пропущенных, первая причина, теги со связью
  через незнакомую таблицу).
- `DATALINK_READWR` и `DATALINK`: элемент абсолютного доступа 0x30 байт,
  символьного — 0x34 + 4·K (K слов пути). Незнакомая длина или область —
  связь не разобрана (данные ПЛК «неизвестно»); по `DATALINK_READWR` одно
  сводное предупреждение.
- Проект ПЛК (`PEData.plf`): проверяются SHA-256 заголовка и каждого кадра,
  цепочка кадров до конца файла, наличие COMMIT; берётся последняя версия
  объекта до последнего COMMIT, надгробия удаляют объект. Сбой — проект не
  используется: консоль `ПРЕДУПРЕЖДЕНИЕ: файл ПЛК - ...`, лист «Ошибки»,
  колонки ПЛК «неизвестно», код 1. Нет файла — строка
  `Файл ПЛК: ... не найден - данные ПЛК: неизвестно`, код 0. Неразобранный
  тег ПЛК или DB — сообщение на лист «Ошибки», код 1.
- Бит `0x2000` в коде типа — массив. Массив выводится как
  `Array [0..N-1] of <тип>`: нижняя граница не хранится, TIA не даёт задать
  её не нулём. Неизвестный код типа — `?` без предупреждения.
- В `panel_data.xlsx` попадают все записи `VAR` в порядке файла, включая
  скрытый `@DiagnosticsIndicatorTag`. Лист «Теги», колонки: Name, Data type,
  Connection, PLC name, PLC tag, Address, Access mode, Acquisition cycle,
  Logged, Source comment, Comment. Значения не угадываются:
  - внутренний тег: Connection `<Internal tag>`, колонки ПЛК пустые;
  - PLC-тег: Connection — имя соединения по номеру из связи; Access mode
    `<symbolic access>`/`<absolute access>`; цикл `100 ms`, `1 s`, `1 min`,
    `1 h` (0 — пусто); Address — только у абсолютного (`%IW44`, `%I1.5`,
    `%DB80.DBW0`, `%T0`), у символьного пусто, как в TIA;
  - ПЛК выбирается так: один ПЛК в проекте и одно соединение — он; иначе по
    IP соединения; не выбран — колонки ПЛК «неизвестно»;
  - символьный I/Q/M/C/T ищется по (ПЛК, область, ID символа), член DB — по
    цепочке LID (`DB.член.член[i]`, тип и комментарий члена), абсолютный — по
    адресу; найден — PLC name, PLC tag, Source comment и тип ПЛК в стиле HMI
    (`String`, `Array [0..N-1] of X`);
  - символьный не найден — «отсутствует в файле ПЛК» в PLC name, PLC tag,
    Source comment, код 0; абсолютный без тега ПЛК — PLC name есть, PLC tag
    и Source comment пустые;
  - нет проекта ПЛК — тип по коду из панели (`USInt/Char`, `DInt/Time`, если
    неразличимы), колонки ПЛК «неизвестно»;
  - Logged и Comment пустые: в файлах их нет.
- Таблица, не подходящая под «каталог смещений», сохраняется целиком в
  `raw.hex.txt` с предупреждением; остальные таблицы обрабатываются.
- Любое предупреждение — неразобранная таблица или запись, таблица,
  сохранённая целиком в `raw.hex.txt`, проблема проекта ПЛК — даёт код
  возврата 1.
- XLSX: лист `0x<lcid>`, колонки `idx` и `str`, текст не превращается в
  формулу, строка длиннее 32767 символов обрезается (так же в
  `panel_data.xlsx`).
- Имя таблицы в имени папки очищается от недопустимых символов.
- HEX-экспорт берёт все таблицы TOC. Перед записью папка `data/out/pdata`
  удаляется целиком: файлы прошлого запуска в ней не остаются.
- Входные файлы — константы в `Program.cs` (`Generates\pdata.fwc`,
  `System\PEData.plf`); непустые переменные окружения `FLEXRT_INPUT` и
  `FLEXRT_PLC` подменяют их. В строках `Файл:` и `Файл ПЛК:` сводки
  печатается фактически прочитанный путь.
- Выходы — константы в `Program.cs` в `data\out`: `PDATA.xlsx`,
  `panel_data.xlsx`, папка `pdata`, лог `logs\flexrt-<дата>.log`. Непустая
  переменная окружения `FLEXRT_OUT` переносит их все в свою папку под
  фиксированными именами (`PDATA.xlsx`, `panel_data.xlsx`, `pdata`,
  `logs\flexrt-<дата>.log`) независимо от значений констант; удаление папки
  `pdata` перед записью и пропуск Excel действуют там же. В строках
  экспортов консоли печатается фактический путь. Значение переменной и
  каталог результата пишутся в лог старта.
- Лог (Serilog): `data/out/logs/flexrt-<дата>.log`, файл на день, хранятся
  последние 14. В лог пишется весь запуск: пути и переменные окружения,
  сводка панели и соединений, предупреждения, сводка проекта ПЛК, итог
  сопоставления, итог и время каждого экспорта, ошибки со стеком, код
  возврата. Консоль от лога не зависит. Непредвиденная ошибка при чтении
  проекта ПЛК или сопоставлении не обрывает программу: «непредвиденная
  ошибка <тип>: …» в консоли и на листе «Ошибки», стек — в лог, код 1.
  Парсеры сами не логируют.
- Если тегов или строк нет, экспорт Excel пропускается сообщением
  `... пропуск`, а его файл от прошлого запуска удаляется. Код возврата при
  пропуске — 0. При ошибке экспорта Excel старый файл остаётся.

## Известные ограничения разбора

- Имени тега ПЛК, имени ПЛК, адреса символьного тега, Comment HMI-тега и
  таблицы HMI-тегов в `pdata.fwc` нет; первые три берутся из проекта ПЛК.
- Выбор ПЛК по IP не работает, если связь интерфейса ведёт не к объекту ПЛК
  (так в A603A0097) — остаётся правило «один ПЛК и одно соединение».
- Не проверены: CPU кроме S7-1500/S7-1200, несколько панелей, комментарии ПЛК
  на нескольких языках (берётся первый непустой), комментарии членов UDT
  против TIA, хэш символа (не расшифрован, не нужен).
- `Data4` — смещение значения в буфере; правило раскладки проверено для
  скаляров, у строк и массивов не установлено.
- Имена таблиц не уникальны (две `PS_BorderedShap`): `FindTable` вернёт
  первую.

## Рабочий стиль

- Сначала устанавливай факты, затем делай выводы. Гипотезу о формате
  проверяй байтами файла и кодом проекта, а не аналогиями.
- Назначение поля считается установленным, только когда оно подтверждено на
  файле с известным содержимым. До этого называй его гипотезой — в коде,
  в комментарии и в отчёте.
- Если источник противоречит гипотезе, исправляй гипотезу, а не подгоняй
  доказательства.
- Прямо называй слабую логику, риски и непроверенные границы.
- Сохраняй несвязанные пользовательские изменения в рабочем дереве.
- Объясняй коротко и по существу, техническими терминами. Без аналогий.

## Не расширяй требования скрыто

Реализуй только:

1. Поведение, которое пользователь запросил явно.
2. Технические действия, объективно необходимые для этого поведения и
   подтверждённые кодом, форматом файла или одобренным требованием.

Не превращай предположение, рекомендацию, распространённый шаблон или
собственное представление о правильном результате в требование пользователя.

Если варианты имеют различимые последствия, не выбирай вариант без явного
решения пользователя. Это относится к изменениям:

- состава и формата выходных файлов;
- того, какие теги, строки и таблицы попадают в вывод;
- текста в консоли и кодов возврата;
- поведения при ошибках разбора;
- путей, имён файлов и каталогов;
- зависимостей и версии .NET.

Перед включением собственного предложения в план:

1. Назови его предложением агента, а не требованием пользователя.
2. Объясни решаемую проблему и доказательства необходимости.
3. Покажи минимальный вариант без предложения.
4. Опиши наблюдаемый результат и побочные эффекты простым языком.
5. Запроси отдельное решение пользователя.

Не добавляй поведение «на всякий случай». Одобрение плана распространяется
только на явно описанные последствия. Если при реализации обнаружилось
неописанное последствие, остановись и снова запроси решение.

Внутренние детали реализации выбирай сам, только если варианты не меняют
вывод, форматы, поведение при ошибках и состав зависимостей.

## Тесты — только по прямому запросу

Не создавай и не изменяй тесты и тестовый проект без прямого запроса
пользователя в текущей задаче. Запуск существующих тестов (`dotnet test
FlexRt.sln`) — обязательная проверка из раздела «Проверки перед
завершением», отдельного запроса для него не нужно. Сверка вывода с эталоном
из того же раздела тоже обязательна.

Если изменение требует нового теста или правки существующего, сообщи, какую
проверку стоит добавить или поменять, и запроси отдельное разрешение. Упавший
тест не подгоняй под новый вывод: покажи отличие пользователю.

## Документация — только по прямому запросу

Не создавай, не изменяй, не переименовывай и не удаляй документацию без
прямого запроса пользователя в текущей задаче. Это относится и к этому файлу.

После правки кода сообщи, какой раздел устарел и какое новое фактическое
поведение следует описать, и запроси отдельное разрешение. Рабочий план держи
в активной задаче, а не в Markdown-файле.

Документация лежит в `docs/`, указатель — `docs/README.md`:

- `docs/формат-fwx/` — что известно о байтах файла, по документу на таблицу;
  у каждого утверждения статус: установлено кодом, наблюдение или гипотеза.
- `docs/текущее-поведение/` — программа глазами того, кто её запускает, без
  имён классов и методов, не длиннее 80 непустых строк.
- `docs/история/` — что было сделано и почему приняты решения.
- `docs/открытые-вопросы.md` — нерешённое: что происходит сейчас, почему это
  важно, какое решение или факт нужен.

Перед правкой разбора таблицы прочитай её документ в `docs/формат-fwx/`, перед
правкой поведения на ошибках — `docs/открытые-вопросы.md`. Если документ
расходится с кодом, остановись и покажи расхождение пользователю.

Называй файлы и каталоги понятными русскими именами в нижнем регистре и
kebab-case, например `формат-fwx/таблица-var.md`. Стандартные имена
(`README.md`, `CLAUDE.md`) не переименовывай.

## Правила кодирования

- Один класс, record, struct или enum — не более 300 строк.
- Один метод — не более 70 строк. Выделяй именованные вспомогательные методы
  до появления длинного процедурного блока.
- Делай структуру блоков неглубокой: guard clauses, небольшие методы, прямой
  поток вместо глубоко вложенных `if`, `for`, `foreach`, `switch`, `try`.
- Каждый тип помещай в отдельный исходный файл в папке по его роли
  (см. «Структура»). Не добавляй вложенные типы.
- Для деталей реализации явно используй `private`. `public` — только для
  того, что вызывается из другого файла.
- Не скрывай нарушение размера переносом несвязанных обязанностей в общий
  утилитный класс.
- Сначала простой прямой код. Абстракция появляется только тогда, когда
  сегодня есть два настоящих применения, а не одно предполагаемое. Без DI,
  интерфейсов «про запас», новых проектов и пакетов.
- Метод делает одно дело, названное его именем.
- Имя говорит, что это за вещь. Не давай имён `Helper`, `Manager`, `Utils`,
  `tmp`, `d`. Исключение — нерасшифрованные поля формата (`D1a`, `Data53`):
  такое имя честно показывает, что назначение неизвестно.
- Плотное выражение — `Select` из LINQ, цепочка `??` — это нормально, дробить
  его не нужно.
- Магическое число формата — либо именованная константа, либо число с
  комментарием-наблюдением («всегда 0x8005»).
- Ошибка всегда сообщает, где она произошла: таблица и смещение
  (`FwxFormatException`).
- Поведение описано в XML-документации над методом и в разделе
  «Установленное поведение». Меняется код — меняются оба места.
- Блок обязателен у каждого оператора, который его допускает, какой бы
  короткой ни была ветка: `if`, `else if`, `else`, `for`, `foreach`,
  `while`, `do`, `using (...)`, `lock`, `try`, `catch`, `finally`. Скобки —
  на отдельных строках (Allman):

  ```csharp
  if (table is null)
  {
      return;
  }
  ```

  Блоками не являются и остаются как есть: члены-выражения `=>`,
  однострочные лямбды, switch-выражения, тернарные операторы,
  `using var x = ...;`, цепочки `??`, инициализаторы объектов и коллекций.
  Правило проверяет сборка: `.editorconfig` (`csharp_prefer_braces`,
  `dotnet_diagnostic.IDE0011.severity = warning`) плюс
  `EnforceCodeStyleInBuild` в `FlexRt.csproj`. Пропущенная скобка — это
  предупреждение сборки, и проверка «0 предупреждений» не проходит.
- Смещения пиши в hex, как в hex-редакторе: `0x34`, `p + 0x14`.
- Над каждым типом, методом, конструктором, константой и статическим полем —
  XML-документация (`/// <summary>`) на русском, в том числе над `private`.
  Описывай, что делает метод, что возвращает, какие случаи обрабатывает и
  какое исключение бросает (`<returns>`, `<exception>`). Поведение метода
  описывай в документации над ним, а не комментариями внутри тела.
- Комментарий внутри метода оставляй только для наблюдения о конкретном поле
  или байте («всегда 0x8005», «почти всегда 227») и для неочевидного шага.
- В `Program.cs` локальные функции документируй обычным комментарием `//`
  над функцией: XML-документация для них не действует.
- Текст в консоли и сообщения об ошибках — на русском.

Новый парсер таблицы панели: файл `Parsing/Panel/<Имя>Parser.cs` с namespace
`FlexRt.Parsing.Panel`, в нём `public static class <Имя>Parser` с методом
`Parse(FwxDocument doc)`. Модель записи — отдельный файл в `Model/Panel/`,
список записей — свойство в `Model/Panel/FwxDocument.cs`. Подключай одной
строкой `TryParse(doc, <Имя>Parser.Parse);` в `Parsing/Panel/FwxReader.cs`,
метод `Read`. Новые данные проекта ПЛК: парсер в `Parsing/Plc/<роль>/`,
объекты — через `PlfFile`, связи — `PlfRelations`, подключение — в
`PlfReader.Read`.
Если число записей должно попасть в сводку, строку сводки добавляй в
`Program.cs`. `HexExporter` берёт любую таблицу TOC сам — править его не
нужно.

Найди таблицу через `FwxDocument.FindTable` — нет таблицы, просто вернись без
сообщений. Выставляй `FwxBinary.Section` для сообщений об ошибках. Элементы
обходи через `FwxReader.CheckedItems` (с проверкой, что элемент лежит в
таблице), если таблица в формате «каталог смещений».
Чтение одной записи держи в приватном `ReadRecord`. Ошибку формата бросай как
`FwxFormatException` и только как неё: `TryParse` превращает в предупреждение
именно это исключение, любое другое оборвёт чтение файла и все экспорты.
Числа из файла проверяй до деления, индексации и выделения памяти. Каждую запись добавляй в список `FwxDocument` сразу
после чтения, чтобы при обрыве разбора частичный результат остался в
документе. `TryParse` кладёт сообщение `FwxFormatException` в
`FwxDocument.Warnings`, поэтому сбой одной таблицы не отменяет остальные.

## Проверки перед завершением

Без отдельного запроса пользователя обязательны:

1. `dotnet build` после последней правки — 0 предупреждений, 0 ошибок.
1a. Проверка в Rider через MCP-сервер `rider`: `get_project_problems` по
   решению и `get_file_problems` по каждому изменённому `.cs`-файлу
   (`rootFolder` — корень репозитория). Все ошибки и предупреждения, включая
   `WEAK WARNING`, устрани и проверь файл повторно до 0. Если исправление
   меняет поведение — не правь, покажи пользователю и запроси решение.
   Если MCP `rider` не подключён, вызов падает или уходит в таймаут — прямо
   сообщи об этом пользователю в отчёте: какой вызов, какая ошибка, какие
   файлы остались непроверенными. Молча пропускать проверку нельзя.
2. Из корня репозитория выполни
   `FLEXRT_INPUT=samples/pdata.fwc dotnet run --project src/FlexRt`
   (папку TIA не трогай), код возврата 0, в сводке
   `Тегов: 16` и `Строк языков: 625`.
2a. `dotnet test FlexRt.sln` — все тесты зелёные.
3. Сверь HEX-вывод с манифестом `samples/expected/pdata.sha256`: из
   `data/out/pdata` выполни `sha256sum -c ../../../samples/expected/pdata.sha256`
   — все `OK`, и файлов в `data/out/pdata` ровно 264 (лишних нет). Если на
   диске есть локальная папка `samples/expected/pdata`, можно вместо этого
   `diff -r data/out/pdata samples/expected/pdata` — без отличий. Лист «Теги» в `panel_data.xlsx` сверь с
   `samples/expected/теги.txt`: по строке на строку листа, ячейки вида
   `A2=Tag_ScreenNumber | B2=UInt` (адрес ячейки, `=`, текст; пустые ячейки
   не пишутся). В `PDATA.xlsx` — лист `0x409` с заголовком и 625 строками.
4. Если правка меняет вывод намеренно, покажи точный diff и объясни каждое
   отличие. Эталон в `samples/expected/` обновляй только после подтверждения
   пользователя.
5. Если затронута обработка ошибок — прогон с `FLEXRT_INPUT=samples/bad.fwc`: понятное
   сообщение, без stack trace, код возврата 1. Если затронут разбор таблицы —
   ещё прогон на копии с испорченной записью этой таблицы: предупреждение с
   таблицей и смещением, код 1, записи до сбоя в выводе.
6. Если затронут разбор `VAR` — прогон с `FLEXRT_INPUT` по каждой копии из
   `data/real/steps/`: код 0,
   число тегов растёт на 1 от шага к шагу.

В итоговом отчёте приведи доказательства: вывод команд и результат проверки
Rider, а не пересказ. Одной
строки «сборка успешна» недостаточно. Прямо укажи, что не проверено — в
первую очередь PLC-теги, другие версии TIA и проекты с несколькими языками.

## Безопасная запись файлов

Передавай инструментам записи абсолютные пути. После серии правок убедись,
что каждый файл существует и не пуст. Не используй `rm -rf` для очистки вне
`data/out`. Не редактируй `bin/` и `obj/`. Не выполняй `git commit` и
`git push` без прямого запроса.
