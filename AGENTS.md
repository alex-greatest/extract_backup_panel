# Инструкции для агента

Правила работы с FlexRt: консольным приложением и окном просмотра `FlexRt.Ui`.

## Что это за проект

FlexRt читает скомпилированную конфигурацию панели TIA Portal — `pdata.fwc` из
папки `Generates` проекта — и данные ПЛК (`System\PEData.plf`, исходный или
выгруженный из ПЛК, или копию карты ПЛК — папку с `SIMATIC.S7S`) и извлекает
из них данные. Цель — развивать извлечение: разбирать новые таблицы и поля.
Форматы закрытые; всё известное о них — в коде, в этом файле, в
`.claude/rules/` и `docs/формат-*`. Каркас формата исторически взят из
R-проекта `rois286/Flex-RT-Configuration-Editor` — он не эталон и не источник
требований, сверять с ним не нужно. Правильно то, что подтверждено байтами
реального файла TIA и решением пользователя. Часть полей разобрана «по
наблюдениям» и помечена комментариями вида «всегда 3».

Консоль за один запуск: печатает сводку (таблицы TOC, строки языков, теги,
события, алармы, классы и группы, экраны, стартовый экран, картинки, `Файл
ПЛК:`); пишет `panel_data.xlsx` (листы «Сводка», «Теги», «Системные события»,
«Дискретные алармы», «Аналоговые алармы», «Классы алармов», «Группы алармов»,
«Экраны», «Ошибки»), `PDATA.xlsx` (строки языков), папку `pdata` (hex всех
таблиц TOC), папку `images` (картинки) и лог `logs\flexrt-<дата>.log` — всё в
`data/out` или в `FLEXRT_OUT`. Окно `FlexRt.Ui` показывает экраны панели и
таблицы листов обеих книг без данных ПЛК, файлов не пишет. Редактирования и
обратной сборки FWX нет.

Аргументов командной строки нет: пути — константы вверху `Program.cs` (решение,
а не недоделка). Непустые `FLEXRT_INPUT`, `FLEXRT_PLC`, `FLEXRT_OUT` подменяют
панель, данные ПЛК и каталог результата — ими пользуются проверки и тесты.

## Стек

- C#, .NET 10. Решение `FlexRt.sln`: `src/FlexRt.Core` — библиотека (разбор,
  сопоставление, экспорты, сценарий запуска; `RootNamespace` `FlexRt`;
  `internal` открыты тестам); `src/FlexRt` — консоль; `src/FlexRt.Ui` — окно
  (WPF + BlazorWebView + Radzen.Blazor, `net10.0-windows10.0.17763.0` — этого
  требует WebView2 в WPF; ссылается только на ядро, тестов нет);
  `tests/FlexRt.Tests` — xUnit, ссылается на ядро и консоль (сборка консоли
  копируется к тестам для запуска отдельным процессом).
- Пакеты: ClosedXML и SharpZipLib — ядро; Serilog и Serilog.Sinks.File —
  консоль; Microsoft.AspNetCore.Components.WebView.Wpf и Radzen.Blazor — окно.
  Других пакетов в программе нет (тесты: xUnit, Microsoft.NET.Test.Sdk,
  xunit.runner.visualstudio). Отдельная библиотека, окно и пакеты — решения пользователя.

## Структура

```
src/FlexRt.Core/
  Binary/      чтение байтов, FwxFormatException
  Model/       данные: Panel/ (Alarms, Screens, Pictures), Plc/ (Plf, Card), Matching/, Summary/
  Parsing/     Panel/ (Alarms, Screens, Pictures) — pdata.fwc; Plc/ (Plf, Card) — данные ПЛК;
               Codes/ — коды областей и типов; Matching/ — TagMatcher, DbPathResolver
  Export/      PanelData/ (Tags, Alarms, Screens) — panel_data.xlsx; Strings/, Hex/, Pictures/
  Extraction/  ExtractionRun — сценарий запуска, IExtractionReporter
src/FlexRt/    Program.cs (пути, лог), ConsoleReporter (весь текст консоли и лога)
src/FlexRt.Ui/ окно просмотра
tests/FlexRt.Tests/  Unit/, Integration/, Extraction/
samples/       образцы pdata.fwc, PEData.plf, карт ПЛК и эталоны expected/
data/          out/ — результат, real/ — локальные копии pdata.fwc (не в git)
```

Namespace совпадает с путём папки. Подробно по классам —
`docs/структура-кода.md`. `.editorconfig` — стиль, который проверяет сборка:
обязательные блоки, file-scoped namespace, namespace = папка.

## Правила по областям

Установленное поведение и известные ограничения каждой области лежат в
`.claude/rules/` — **не меняй их без решения пользователя**. Claude подгружает
файл сам, когда открывает файлы области; другие агенты — прочитай файл области
перед правкой:

- `формат-панели.md` — таблицы `pdata.fwc`, `VAR`, `DATALINK`, ошибки разбора,
  на чём проверено, как добавить новый парсер;
- `теги.md` — лист «Теги», массивы, сопоставление с ПЛК;
- `проект-плк.md` — `PEData.plf`, карта ПЛК;
- `алармы.md` — системные события, дискретные и аналоговые алармы, классы, группы;
- `экраны-и-картинки.md` — экраны, стартовый экран, картинки;
- `выходы-и-запуск.md` — сценарий запуска, «Сводка», Excel, hex, пути, лог,
  коды возврата, «не поддерживается»;
- `окно.md` — окно просмотра;
- `тесты-и-образцы.md` — тестовый проект, образцы, эталоны, данные вне git.

## Модульность

- Зависимости в одну сторону: `Binary` ← `Model` ← `Parsing` ← `Export` ←
  `Extraction` ← консоль и окно. Папка пользуется только теми, что левее неё:
  парсер не знает про экспортёры, экспортёр не вызывает `Parse` парсеров,
  модели зависят только от `Binary`. Неожиданный `using` — зависимость не в ту
  сторону. `Parsing/Panel` и `Parsing/Plc` друг от друга не зависят, общее у
  них — `Parsing/Codes`.
- Ядро не пишет в консоль и не знает про Serilog: всё для пользователя идёт
  через `IExtractionReporter`. Библиотека и интерфейс с одной реализацией —
  решение пользователя, исключение из правила «без интерфейсов про запас и
  новых проектов».
- Одна таблица — один парсер, один выходной формат — один экспортёр. Новая
  таблица — новые файлы плюс точечные строки подключения; логику существующих
  парсеров и экспортёров править не приходится.
- Модели — только данные, без логики разбора и форматирования.

## Источники фактов о формате

1. Код проекта, его XML-документация и комментарии-наблюдения.
2. Этот файл, `.claude/rules/`, `docs/формат-fwx/`, `docs/формат-plf/`,
   `docs/формат-карты/`.
3. Байты реального `pdata.fwc`, сопоставленные с известным проектом TIA, —
   единственный способ установить назначение поля. Лучше всего — шаговые копии:
   пользователь меняет одно свойство, компилирует и сохраняет `pdata.fwc` под
   новым именем; сравниваются соседние копии.

Синтетических файлов нет и не создаётся; `pdata.pwx` бесполезен (168 байт,
зашифрованное администрирование пользователей). Называй вывод проверенным
только на том, на чём он проверен (см. правила областей).

## Рабочий стиль

- Сначала факты, затем выводы. Гипотезу о формате проверяй байтами и кодом, а
  не аналогиями. Поле установлено, только когда подтверждено на файле с
  известным содержимым; до этого — гипотеза в коде, комментарии и отчёте.
- Источник противоречит гипотезе — исправляй гипотезу.
- Прямо называй слабую логику, риски и непроверенные границы.
- Сохраняй несвязанные пользовательские изменения в рабочем дереве.
- Объясняй коротко, техническими терминами, без аналогий.

## Не расширяй требования скрыто

Реализуй только явно запрошенное и технически необходимое для этого
(подтверждённое кодом, форматом или одобренным требованием). Предположение,
рекомендация, распространённый шаблон или собственное представление о
правильном результате — не требование пользователя. Не добавляй поведение «на
всякий случай».

Варианты с различимыми последствиями без решения пользователя не выбирай. Это
касается состава и формата выходных файлов, того, что попадает в вывод, текста
консоли и кодов возврата, поведения при ошибках разбора, путей и имён, зависимостей
и версии .NET.

Своё предложение в плане: назови его предложением агента, объясни проблему и
доказательства, покажи минимальный вариант без него, опиши видимый результат и
побочные эффекты, запроси отдельное решение. Одобрение плана покрывает только
описанные последствия; всплыло неописанное — остановись и спроси. Внутренние
детали выбирай сам, если они не меняют вывод, форматы, ошибки и зависимости.

## Тесты — только по прямому запросу

Не создавай и не меняй тесты и тестовый проект без прямого запроса в текущей
задаче. Запуск существующих тестов и сверка с эталоном — обязательные проверки,
отдельного запроса не нужно. Нужен новый тест или правка существующего — скажи,
какую проверку добавить или поменять, и запроси разрешение. Упавший тест не подгоняй под новый вывод: покажи отличие.

## Документация — только по прямому запросу

Не создавай, не меняй, не переименовывай и не удаляй документацию (и этот
файл, и `.claude/rules/`) без прямого запроса в текущей задаче. После правки
кода скажи, какой раздел устарел и что описать, и запроси разрешение. Рабочий
план держи в задаче, а не в Markdown-файле. `AGENTS.md` — точная копия этого
файла для других агентов: меняется только вместе с ним, тем же коммитом.

`docs/` (указатель — `docs/README.md`): `формат-fwx/`, `формат-plf/`,
`формат-карты/` — байты форматов, по документу на таблицу или объект, у каждого утверждения статус (установлено
кодом, наблюдение, гипотеза); `текущее-поведение/` — программа глазами
пользователя, без имён классов, ≤ 80 непустых строк на файл; `история/` — что
сделано и почему; `открытые-вопросы.md` — нерешённое: что происходит, почему
важно, какое решение или факт нужен. Перед правкой разбора
таблицы прочитай её документ, перед правкой поведения на ошибках —
`открытые-вопросы.md`; документ расходится с кодом — остановись и покажи
расхождение. Имена файлов — русские, нижний регистр, kebab-case; стандартные
имена (`README.md`, `CLAUDE.md`, `AGENTS.md`) не переименовывай.

## Правила кодирования

- Тип — не более 300 строк, метод — не более 70; структура неглубокая (guard
  clauses, небольшие методы); именованные вспомогательные методы выделяй до
  появления длинного процедурного блока. Метод делает одно дело, названное его
  именем.
- Каждый тип — в своём файле в папке по роли, без вложенных типов. Явный
  `private`; `public` — только для вызываемого из другого файла. Не прячь
  нарушение размера в общий утилитный класс.
- Сначала простой прямой код; абстракция — только при двух настоящих
  применениях. Без DI (кроме регистрации служб окна), интерфейсов «про запас»,
  новых проектов и пакетов.
- Имя говорит, что это за вещь: без `Helper`, `Manager`, `Utils`, `tmp`, `d`
  (кроме нерасшифрованных полей формата: `D1a`, `Data53`). Плотный LINQ и `??`
  дробить не нужно.
- Магическое число формата — константа или число с комментарием-наблюдением
  («всегда 0x8005»). Смещения — в hex: `0x34`, `p + 0x14`.
- Ошибка формата — `FwxFormatException` с таблицей и смещением.
- Блок `{ }` обязателен у `if`/`else if`/`else`/`for`/`foreach`/`while`/`do`/
  `using (...)`/`lock`/`try`/`catch`/`finally`, как бы коротка ни была ветка;
  скобки на отдельных строках (Allman). Блоками не являются и остаются как есть:
  члены-выражения `=>`, однострочные лямбды, switch-выражения, тернарные
  операторы, `using var x = ...;`, цепочки `??`, инициализаторы. Проверяет
  сборка (`.editorconfig` IDE0011 + `EnforceCodeStyleInBuild` в каждом
  `.csproj`): пропущенная скобка — предупреждение, и «0 предупреждений» не
  проходит.
- Над каждым типом, методом, конструктором, константой и статическим полем —
  `/// <summary>` на русском, в том числе над `private` и членами `@code` в
  `.razor`; `<returns>`, `<exception>`. Поведение — в документации над методом
  и в правилах области: меняется код — меняются оба. Комментарий внутри метода —
  только наблюдение о поле или неочевидный шаг. Локальные функции `Program.cs` —
  обычный `//`. Приватные поля экземпляра — `_camelCase`.
- Текст консоли и сообщения об ошибках — на русском.

## Проверки перед завершением

Обязательны без отдельного запроса:

1. `dotnet build FlexRt.sln` — 0 предупреждений, 0 ошибок (запущенное окно
   блокирует сборку — см. `окно.md`). Меняется `FwxReader`, построитель таблицы
   листа (`*Table`, `SummaryRows`, `TagStatistics`) или модели экранов — открой
   в окне `samples/screens/05_popup.fwc`.
2. Rider MCP `rider`: `get_project_problems` (`rootFolder` — корень репозитория)
   и `get_file_problems` по каждому изменённому `.cs`/`.razor` — до 0, включая
   `WEAK WARNING`. Исправление меняет поведение — не правь, спроси. Rider не
   отвечает — прямо скажи в отчёте, какой вызов, какая ошибка, какие файлы не
   проверены; молча пропускать нельзя.
3. `FLEXRT_INPUT=samples/pdata.fwc dotnet run --project src/FlexRt` из корня
   (папку TIA не трогай): код 0, `Тегов: 16`, `Строк языков: 625`.
4. `dotnet test FlexRt.sln` — все зелёные.
5. Из `data/out/pdata`: `sha256sum -c ../../../samples/expected/pdata.sha256` —
   все `OK`, файлов ровно 264 (есть локальная `samples/expected/pdata` — можно
   `diff -r data/out/pdata samples/expected/pdata`). Лист «Теги» — как
   `samples/expected/теги.txt` (ячейки `A11=Tag_ScreenNumber | B11=UInt`, пустые
   не пишутся, сверху 7 строк статистики, `A1=Всего тегов | B1=16`); `PDATA.xlsx` — лист `0x409`, заголовок и 625 строк.
6. Вывод меняется намеренно — покажи точный diff и объясни каждое отличие;
   эталоны `samples/expected/` — только после подтверждения пользователя.
7. Затронута обработка ошибок — прогон с `FLEXRT_INPUT=samples/bad.fwc`:
   понятное сообщение без stack trace, код 1. Затронут разбор таблицы — ещё
   копия с испорченной записью: предупреждение с таблицей и смещением, код 1,
   записи до сбоя в выводе.
8. Затронут разбор `VAR` — прогон по каждой копии `data/real/steps/`: код 0,
   тегов на 1 больше от шага к шагу.

В отчёте — доказательства (вывод команд, результат Rider), а не пересказ:
одной строки «сборка успешна» недостаточно.
Прямо укажи, что не проверено: PLC-теги, другие версии TIA, несколько языков.

## Безопасная запись файлов

Абсолютные пути в инструментах записи; после серии правок — файлы существуют и
не пусты. Не используй `rm -rf` вне `data/out`, не редактируй `bin/` и `obj/`.
Не выполняй `git commit` и `git push` без прямого запроса.
