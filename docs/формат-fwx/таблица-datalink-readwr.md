# Таблица DATALINK_READWR

`DATALINK_READWR` — таблица со связями тегов с ПЛК: номер блока данных и
смещение в нём, позиция бита, ширина значения, код типа и цикл
опроса в миллисекундах. Текущая программа не разбирает записи этой таблицы,
а сохраняет её байты через общий HEX-экспорт. Ниже сохранена раскладка
удалённого разбора как материал для будущего исследования, а не как текущий
выход программы.

Таблица обычная: заголовок 0x34 → каталог смещений → блок данных (см.
[общая-структура.md](общая-структура.md)). В прежнем коде обход выполнялся
через `FwxReader.Items`, а адрес собирался из полей одной записи. Всё ниже
взято из удалённого кода прежнего разбора и проверено на **синтетическом**
`samples/sample.fwx` (2 записи). Настоящего `PDATA.FWX` в проекте нет, и обе
условные ветки разбора в синтетике не встречаются — они описаны по коду, а
не по байтам.

Соседние документы: [общая-структура.md](общая-структура.md),
[таблица-var.md](таблица-var.md),
[таблица-stringstore.md](таблица-stringstore.md).

## Чтение записи — последовательность

Запись читается одним курсором `k` подряд, без таблицы смещений: каждое
следующее поле начинается там, где остановился курсор. Порядок чтения в коде
и есть раскладка записи. Ниже `R` — смещение элемента (`item.Offset`),
смещения даны для основного случая `d0a == 0` и `d9 != 2`.

| Смещ. | Разм. | В коде       | Значение                        | Статус |
|-------|-------|--------------|---------------------------------|--------|
| R+0x00 | 4 | `D1a`       | «всегда 1»                       | наблюдение |
| R+0x04 | 4 | `D1b`       | «всегда 1»                       | наблюдение |
| R+0x08 | 4 | `D10`       | «всегда 0xa»                     | наблюдение |
| R+0x0c | 2 | `D5`        | «всегда 5»                       | наблюдение |
| R+0x0e | 2 | `D32773`    | «всегда 0x8005»                  | наблюдение |
| R+0x10 | 4 | `Acq`       | цикл опроса, мс                  | установлено прежним кодом |
| R+0x14 | 2 | `D258`      | «всегда 0x102»                   | наблюдение |
| R+0x16 | 2 | `D0a`       | «всегда 0»; управляет веткой адреса | установлено прежним кодом |
| R+0x18 | 4 | `D9`        | «всегда 9 (для HTTP boolean — 6)»; управляет шириной поля `bits` | установлено прежним кодом |
| R+0x1c | 2 | `D0b`       | «всегда 0»                       | наблюдение |
| R+0x1e | 1 | `DataType`  | код типа datalink, см. исторический справочник кодов ниже | установлено прежним кодом |

Дальше раскладка зависит от `D0a`.

### Ветка `d0a == 0`: адрес есть

```csharp
database       = b.D2(k += 1);   // R+0x1f
databaseOffset = b.D2(k += 2);   // R+0x21
k += 1;                          // курсор -> R+0x22
```

| Смещ. | Разм. | В коде | Значение | Статус |
|-------|-------|--------|----------|--------|
| R+0x1f | 2 | `Db`       | номер блока данных DB           | гипотеза |
| R+0x21 | 2 | `DbOffset` | смещение внутри DB              | гипотеза |
| R+0x23 | 1 | `BitPosition` | номер бита                   | гипотеза |

Оба слова читаются с нечётного смещения — выравнивания у них нет. Байт
R+0x22 курсор проходит, не читая.

При `d0a != 0` эти три поля не читаются, `Db` и `DbOffset` остаются `null`,
а `Address` равен `null`. Курсор при этом не сдвигается на 4 байта, поэтому
`BitPosition` и все последующие поля лежат на 4 байта ближе к началу записи:
`BitPosition` по R+0x1f, `D24` по R+0x20 и так далее. В синтетике эта ветка
не встречается: у обеих записей `d0a == 0`.

### Ветка `d9 != 2`: три слова, `bits` шириной 2 байта

```csharp
d24  = b.D2(k += 1);   // R+0x24
d26  = b.D2(k += 2);   // R+0x26
bits = b.D2(k += 2);   // R+0x28
```

| Смещ. | Разм. | В коде | Значение | Статус |
|-------|-------|--------|----------|--------|
| R+0x24 | 2 | `D24`  | не расшифровано            | гипотеза |
| R+0x26 | 2 | `D26`  | не расшифровано            | гипотеза |
| R+0x28 | 2 | `Bits` | ширина значения в битах    | установлено прежним кодом |

Имена `D24` и `D26` совпадают со смещениями именно в этой ветке; остальные
неразобранные поля названы по своему значению (`D1a` = 1, `D10` = 0xa,
`D32773` = 0x8005, `D258` = 0x102).

### Ветка `d9 == 2`: `bits` шириной 1 байт

```csharp
bits = b.D1(k += 1);   // R+0x24, один байт
...
arraySize = b.D2(k += 2);  // R+0x26
```

`D24` и `D26` остаются `null`, `Bits` читается одним байтом по R+0x24, но
курсор после него сдвигается на 2 (`k += 2`): байт R+0x25 пропускается и
никогда не читается. Из-за этого следующие поля лежат на 4 байта ближе к
началу записи, чем в основной ветке, а вся запись короче на 4 байта.
В синтетике эта ветка тоже не встречается: у обеих записей `d9 == 9`.

### Хвост записи

Смещения — для основного случая (`d0a == 0`, `d9 != 2`).

| Смещ. | Разм. | В коде      | Значение                   | Статус |
|-------|-------|-------------|----------------------------|--------|
| R+0x2a | 2 | `ArraySize` | размер массива, «обычно 1» | наблюдение |
| R+0x2c | 4 | `D7`        | «всегда 7»                 | наблюдение |

Полная длина записи в основной ветке — 0x30 = 48 байт (R+0x00…R+0x2f); при
`d9 == 2` — 44 байта. Код длину записи не проверяет: границы элемента задаёт
каталог смещений, и лишние байты в конце элемента остаются непрочитанными.

## Цикл опроса

`Acq` — 32-битное число по R+0x10, в миллисекундах. В прежнем выводе оно
попадало в колонку `Acquisition cycle [ms]` страницы `tags.html` как есть,
без пересчёта. Единица измерения — знание из R-проекта; кодом она не
проверялась. В синтетике `Acq = 500` у обеих записей.

## Код типа

`DataType` — один байт по R+0x1e. В прежнем разборе его обрабатывал
`TypeCatalog.Datalink`: допустимы коды 0…14, всё остальное (и `null`) даёт
`UNKNOWN`. Поиск в историческом `types.csv` шёл по колонке
`datalink_code`: сначала строка, где
заполнена и колонка `code` (тип `VAR`), затем любая строка с таким
`datalink_code`.

| Код | `datalink_name` | Строка `types.csv` |
|-----|-----------------|--------------------|
| 0   | Char            | `0x90 CHAR`   |
| 1   | Byte            | `0x91 BYTE`   |
| 2   | Int             | `0x82 INT`    |
| 3   | Word            | `0x92 UINT`   |
| 4   | Dint/Time       | `0x83 LONG`   |
| 6   | Real            | `0x84 FLOAT`  |
| 7   | Bool            | `0x8b BOOL`   |
| 8   | String          | `0x88 STRING` |
| 9   | Timer           | `0x93 ULONG`  |
| 10  | Counter         | строка без кода `VAR` |
| 11  | Date and time   | `0x87 VT_DATE` |
| 12  | Time of day     | строка без кода `VAR` |
| 13  | Date and time   | `0x85 DOUBLE` |
| 14  | StringChar      | строка без кода `VAR` |

Кода 5 в `types.csv` нет — он даст `UNKNOWN`. Код 13 встречается дважды,
выигрывает строка `0x85 DOUBLE`, потому что у неё заполнена колонка `code`.
Тип из datalink подставлялся в прежний `tags.html` только тогда, когда тип из
[VAR](таблица-var.md) не распознан.

## Позиция бита и буква адреса

`Bits2Char` переводит число бит в букву адреса по целой части `log2`:

```csharp
private static readonly string[] AddressChars = ["X", "", "", "B", "W", "D", "D"];
bits is >= 1 and < 128 ? AddressChars[BitOperations.Log2((uint)bits)] : "?";
```

| `Bits`  | log2 | Буква |
|---------|------|-------|
| 1       | 0    | `X`   |
| 2…3     | 1    | пусто |
| 4…7     | 2    | пусто |
| 8…15    | 3    | `B`   |
| 16…31   | 4    | `W`   |
| 32…63   | 5    | `D`   |
| 64…127  | 6    | `D`   |
| 0 или ≥ 128 | —  | `?`   |

Целая часть логарифма означает, что промежуточные значения (например 9 или
20) дадут ту же букву, что 8 и 16. Встречаются ли они в настоящем файле —
неизвестно; в синтетике только 1 и 16.

Адрес собирается в `DbAddress`:

```
DB<Db>DB<буква><DbOffset>          и для буквы X дополнительно .<BitPosition>
```

Примеры из синтетики: `DB7DBX12.3` (bits = 1) и `DB7DBW12` (bits = 16).
`BitPosition` попадает в адрес только при букве `X`. Если `d0a != 0`,
`Address` оставался `null` и колонка адреса в прежнем `tags.html` была пуста.

## Размер массива

`ArraySize` в записи datalink читался и сохранялся в модели, но в вывод не
шёл: прежний `HtmlExporter` брал размер массива из тега
([VAR](таблица-var.md), поле `ArraySize`).

## Аннотированный дамп записи

Запись 1 из `samples/sample.fwx`: смещение 0x118, длина 0x30 байт,
сгенерирована как `link(bits=1, kind=7)`.

```
00000118  01 00 00 00      R+0x00 D1a      = 1
0000011c  01 00 00 00      R+0x04 D1b      = 1
00000120  0a 00 00 00      R+0x08 D10      = 0xa
00000124  05 00            R+0x0c D5       = 5
00000126  05 80            R+0x0e D32773   = 0x8005
00000128  f4 01 00 00      R+0x10 Acq      = 500 мс
0000012c  02 01            R+0x14 D258     = 0x102
0000012e  00 00            R+0x16 D0a      = 0      -> адрес читается
00000130  09 00 00 00      R+0x18 D9       = 9      -> bits шириной 2 байта
00000134  00 00            R+0x1c D0b      = 0
00000136  07               R+0x1e DataType = 7      -> Bool
00000137  07 00            R+0x1f Db       = 7
```

Байт 0x13a курсор проходит, не читая (`k += 1` после `DbOffset`). Итог:

Запись 2 (0x148, те же 0x30 байт, `link()`) отличается двумя полями:
`DataType = 2` (`Int`) по 0x166 и `Bits = 0x10` по 0x170 → `DB7DBW12`,
без `.бит`.

## Связь с VAR

У записи нет ни имени тега, ни ссылки на него. В прежнем разборе
`Datalink.Idx` был равен `item.Index`, то есть **позиции записи в таблице**,
а не значению из файла. Прежний `HtmlExporter` брал запись как
`doc.Datalinks[tag.Idx]`, где `Tag.Idx` — поле по p+0x06 записи
[VAR](таблица-var.md). По наблюдению из прежних правил проекта, `Tag.Idx` был
сквозным индексом только при `Data53 == 0x35`; у остальных тегов бралась
чужая запись. В синтетике условие выполнялось у обоих тегов, так что
ошибочный случай не наблюдался.

## Чего мы не знаем

- **Область памяти.** Поле, отличающее `M`, `I`, `Q`, `T`, `C` от `DB`, не
  найдено. Адрес всегда собирается по шаблону `DB…`. Кандидаты на это поле —
  `D9`, `D24`, `D26`, `D0a`. Проверить можно только на настоящем
  `PDATA.FWX`, где заведомо есть тег на меркере или входе.
- Драйверы, отличные от S7. Формат записи для них не проверялся; возможно,
  меняется и состав полей, и смысл `D9`.
- Смысл `D1a`, `D1b`, `D10`, `D5`, `D32773`, `D258`, `D0b`, `D24`, `D26`,
  `D7`.
- Что означает `D9 == 6` («для HTTP boolean») и какие ещё значения бывают
  кроме 9, 6 и 2.
- Ветки `d0a != 0` и `d9 == 2` описаны только по коду: в синтетическом файле
  таких записей нет.
- Есть ли в таблице записи, не привязанные ни к одному тегу.
