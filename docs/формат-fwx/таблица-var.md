# Таблица VAR

`VAR` — таблица с записями тегов (переменных) HMI: имя тега, код типа, размер
массива и индекс, по которому в прежнем разборе бралась запись адреса в
[DATALINK_READWR](таблица-datalink-readwr.md). Текущая программа не разбирает
записи `VAR`: она сохраняет таблицу в hex через общий экспортёр. Ниже
сохранена раскладка и полевая номенклатура прежнего разбора как материал для
будущего исследования, а не описание текущей функции.

Таблица устроена как обычная: заголовок 0x34 → каталог смещений → блок
данных (см. [общая-структура.md](общая-структура.md)). Прежний парсер
обходил её через `FwxReader.Items` и читал каждый элемент в отдельной
функции. Сведения взяты из удалённого кода прежнего разбора и проверены на
байтах **синтетического** `samples/sample.fwx` (2 записи). Настоящего
`PDATA.FWX` в проекте нет, поэтому назначение большинства полей записи
остаётся гипотезой.

Соседние документы: [общая-структура.md](общая-структура.md),
[таблица-datalink-readwr.md](таблица-datalink-readwr.md),
[таблица-stringstore.md](таблица-stringstore.md).

## Как читается запись

`ReadRecord` получает элемент таблицы (`item.Offset`, `item.Length`) и читает
его в два приёма: сначала «шапку» с именем, потом блок данных. Это описание
удалённого разбора, текущего чтения записей нет.

Шапка:

1. `type = D2(tagOffset)` — слово типа записи. Комментарий в коде: «3 или
   0xb (3+8 — вероятно флаг)».
2. `name = GetName(tagOffset + 2)` — длина имени в **символах** в слове по
   +0x02, затем столько же символов UTF-16LE с +0x04.
3. `len = D2(tagOffset + 2)` — та же длина, читается вторично, чтобы
   посчитать выравнивание.

Выравнивание и начало блока данных:

```csharp
int align = (len * 2) % 4;
long p = tagOffset + 4 + len * 2 + align;
```

`len * 2` — длина имени в байтах, она всегда чётная, поэтому `align` равен 0
или 2: имя дополняется нулями до кратности 4. Два байта слова типа плюс два
байта длины дают 4, так что начало блока данных `p` кратно 4 относительно
начала записи.

## Раскладка блока данных

Смещения — от `p`. Столбец «в коде» — имя переменной и свойство прежней
модели записи.

| Смещ. | Разм. | В коде       | Значение                                  | Статус |
|-------|-------|--------------|-------------------------------------------|--------|
| p+0x00 | 4 | `DataLen`     | длина/вид блока данных, «почти всегда 2»; управляет раскладкой | установлено прежним кодом |
| p+0x04 | 2 | `Data53`      | «почти всегда 0x35»                        | наблюдение |
| p+0x06 | 2 | `Idx`         | номер записи в DATALINK_READWR             | гипотеза прежнего разбора |
| p+0x08 | 2 | `DataOffset`  | «почти всегда 0»                           | наблюдение |
| p+0x0a | 4 | `Data80E3`    | «всегда 0x80E3»                            | наблюдение |
| p+0x0e | 2 | `Data00`      | «всегда 0»                                 | наблюдение |

Дальше — только при `DataLen > 0`; при `DataLen == 0` эти поля остаются
`null` (тип тега не читается вообще):

| Смещ. | Разм. | В коде       | Значение                                  | Статус |
|-------|-------|--------------|-------------------------------------------|--------|
| p+0x10 | 2 | `Data01`      | «всегда 0»                                 | наблюдение |
| p+0x12 | 2 | `Data227`     | «почти всегда 227, у массивов 0x8000 / 0x8019» | наблюдение |
| p+0x14 | 2 | `DataType`    | код типа, см. исторический справочник кодов ниже | установлено прежним кодом |
| p+0x16 | 2 | `ArraySize`   | размер массива, «обычно 1»                 | установлено прежним кодом |
| p+0x18 | 2 | `DataPos`     | не расшифровано                            | гипотеза |
| p+0x1a | 2 | `Data02`      | не расшифровано                            | гипотеза |
| p+0x1c | 2 | `Data03`      | не расшифровано                            | гипотеза |
| p+0x1e | 2 | `Data04`      | не расшифровано                            | гипотеза |

«Установлено прежним кодом» здесь значит: значение реально влияло на
прежний разбор или HTML-вывод (`DataType` и `ArraySize`). Что именно эти
поля означают в терминах WinCC flexible, на синтетике не проверяется.

## Сдвиг на 8 байт при `DataLen == 3`

Если `DataLen == 3`, содержательные поля лежат на 8 байт дальше. Код сначала
читает все восемь полей по «обычным» смещениям, а затем переприсваивает:

```csharp
if (dataLen == 3)
{
    data227 = data02;          // фактически p+0x1a
    dataType = data03;         // фактически p+0x1c
    arraySize = data04;        // фактически p+0x1e
    dataPos = b.D2(p + 0x20);
    data02 = b.D2(p + 0x22);
    data03 = b.D2(p + 0x24);
    data04 = b.D2(p + 0x26);
}
```

То есть при `DataLen == 3`:

| Смещ. | В коде      |
|-------|-------------|
| p+0x1a | `Data227`  |
| p+0x1c | `DataType` |
| p+0x1e | `ArraySize`|
| p+0x20 | `DataPos`  |
| p+0x22 | `Data02`   |
| p+0x24 | `Data03`   |
| p+0x26 | `Data04`   |

Важная деталь: `Data01` при сдвиге **не** переприсваивается и остаётся
прочитанным по p+0x10, а значения, прочитанные по p+0x12, p+0x14, p+0x16 и
p+0x18, отбрасываются. Почему сдвиг именно 8 байт и что лежит в p+0x12…p+0x19
при `DataLen == 3` — не установлено. Проверять пришлось бы на настоящем
файле; в синтетике эти байты нулевые.

## Исторический справочник кодов типов

Прежний разбор обрабатывал код типа из `DataType` через `TypeCatalog.Tag` и
файл `types.csv`, которого больше нет в рабочем проекте:

- если код `>= 0x2000` — это массив, из кода вычитается `0x2000`, и дальше
  ищется базовый тип;
- в историческом `types.csv` искалась строка с таким значением в колонке
  `code`
  (первая колонка, hex-запись `0x82`);
- ничего не нашлось или `DataType == null` — возвращается строка с кодом 0,
  то есть `UNKNOWN`.

Колонки исторического `types.csv`: `code, name, datalink_code, datalink_name, len, min,
max`. Для `VAR` значимы `code`, `name`, `min`, `max`. Примеры: `0x82 INT`,
`0x8b BOOL`, `0x88 STRING`, `0x92 UINT`. Колонки `datalink_code` и
`datalink_name` относятся к [DATALINK_READWR](таблица-datalink-readwr.md).

Если тип из `VAR` не распознавался (`UNKNOWN`) и для тега находилась запись
datalink, прежний `HtmlExporter.ResolveType` подставлял тип из datalink.
Именно так в синтетике прежний HTML-вывод показывал тег `Flag` с
`DataLen == 0`.

## Размер массива

`ArraySize` — число элементов. Прежний `HtmlExporter` брал
`Math.Max(1, tag.ArraySize ?? 1)`: `0` и `null` дают одну строку вывода.
При размере > 1 в таблицу выводится строка на элемент: имя получает номер
элемента с нуля (`Температура[0]`), а имя типа — размер массива (`INT[2]`).

## Аннотированный дамп записи

Тег 1 из `samples/sample.fwx`, элемент 1 таблицы `VAR`: смещение 0x7c,
длина 0x44 байта. Сгенерирован как `tag("Температура", 1, 0x2082, 2, 3)`.

```

0000007e  0b 00                    длина имени = 11 символов
00000080  22 04 35 04 3c 04 3f 04  "Темп"
00000088  35 04 40 04 30 04 42 04  "ерат"
00000090  43 04 40 04 30 04        "ура"          имя занимает 0x80..0x95
00000096  00 00                    align = (11*2)%4 = 2, дополнение нулями
--- p = 0x7c + 4 + 22 + 2 = 0x98 ---
00000098  03 00 00 00              p+0x00 DataLen   = 3   -> сдвиг на 8
0000009c  35 00                    p+0x04 Data53    = 0x35
0000009e  01 00                    p+0x06 Idx       = 1
000000a0  00 00                    p+0x08 DataOffset= 0
000000a2  e3 80 00 00              p+0x0a Data80E3  = 0x80e3
000000a6  00 00                    p+0x0e Data00    = 0
000000a8  00 00                    p+0x10 Data01    = 0
000000aa  00 00                    p+0x12 (отброшено при DataLen == 3)
000000ac  00 00                    p+0x14 (отброшено)
000000ae  00 00                    p+0x16 (отброшено)
000000b0  00 00                    p+0x18 (отброшено)
000000b2  e3 00                    p+0x1a Data227   = 227
000000b4  82 20                    p+0x1c DataType  = 0x2082 -> массив 0x82
000000b6  02 00                    p+0x1e ArraySize = 2
000000b8  00 00                    p+0x20 DataPos   = 0

000000bc  00 00                    p+0x24 Data03    = 0
000000be  00 00                    p+0x26 Data04    = 0
```

`DataType = 0x2082` → `0x2082 - 0x2000 = 0x82` → `INT`, `ArraySize = 2` →
в прежнем `tags.html` две строки `Температура[0]` и `Температура[1]` с типом
`INT[2]` и пределами −32768…32767 из исторического `types.csv`.

Тег 2 того же файла (смещение 0xc0, 0x1c байт) собран как
`tag("Flag", 0, length=0)`: имя `Flag` (4 символа, `align = 0`,
`p = 0xcc`), `DataLen = 0` — блок типа не читается, `DataType`,
`ArraySize` и остальные `null`. `Idx = 0`, поэтому адрес и тип берутся
из записи datalink №0.

## Связь с DATALINK_READWR

Прежний `HtmlExporter` брал `doc.Datalinks[tag.Idx]`, то есть `Tag.Idx`
трактовался как **позиция записи в списке** `DATALINK_READWR`. Если `Idx` не
меньше числа записей, адрес и цикл опроса в строке оставались пустыми.

По наблюдению, записанному в прежних правилах проекта, `Idx` — сквозной индекс только при
`Data53 == 0x35`; у остальных тегов будет взята чужая запись. В синтетике
`Data53 == 0x35` у обоих тегов, так что противоположный случай здесь не
представлен.

## Чего мы не знаем

- `DataLen == 0`: тип тега не читается вообще. Что в этом случае лежит
  вместо блока типа и какие теги так выглядят в настоящем файле —
  не установлено.
- Смысл `Data53` (0x35), `Data227` (227, у массивов 0x8000 / 0x8019),
  `Data80E3`, `Data01`, `Data00`, `DataOffset`, `DataPos`, `Data02`…`Data04`.
- Почему `DataLen == 3` сдвигает поля на 8 байт и бывают ли другие значения
  `DataLen` со своей раскладкой. Комментарий кода: «почти всегда 2».
- Значение слова `type` (3 или 0xb) в начале записи.
- Условие, при котором `Idx` действительно сквозной (наблюдение:
  `Data53 == 0x35`).
- Где в записи хранятся начальное значение, комментарий тега и признак
  «внутренний тег / тег ПЛК» — в разобранных полях их нет.
